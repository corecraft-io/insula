# ADR-0008 冷热两级租户：空闲租户的装配回收

- **状态**：Proposed（尚未实施。首次落地应当是**默认关闭**的 opt-in，理由见「决定」第 5 条）
- **记录日期**：2026-10-01
- **落实于**：计划落在 `tenant`、`shard`、`admit`、`metrics`、`insula`（本文件只记录决定，不含实现）

## 背景

设计文档 §5「两级租户：热常驻 / 冷按需」写了一条容量策略，而实现里**不存在任何空闲回收路径**。今天是：**开通即常驻，直到注销**。

先说清代价，因为"省内存"这句话在这种平台上经常被高估：

| 量 | 实测 | 出处 |
| --- | --- | --- |
| 每租户 fiber 数 | **12.00**（100/1000 规模平直） | `tenant.BenchmarkFiberFootprint` |
| 每租户常驻内存 | **30 377 B** | 同上 |
| 分片容量分母 | 2000 租户/片 ≈ 60 MB/片 | `BENCHMARK.md` |

关键在于这 12 个 fiber 的**构成**：1 个租户根 + 5 个租户级服务入口（`models`/`memory`/`guard`/`tools`/`caps`）+ 5 个能力探测入口（一服务一个）+ 1 个会话分组容器 = **12**。而 `BenchmarkFiberFootprint` 的夹具只 `Provision`、**不建任何会话**。

于是有一条容易被想反的结论：

> **会话级回收省不到什么。** 一个租户就算一个会话都没有，也已经常驻 12 fiber。会话只在 12 之上再叠加。所以「把空闲会话摘掉」这条最直觉的做法，几乎不触动设计 §5 想解决的那个量。

真正能触动的只有一个动作：**把整棵租户子树摘掉**。

而今天唯一能摘子树的路径是 `tenant.Manager.Deprovision`，它**清除记忆**——这是刻意的（见 `tenant.Spec.Disabled` 的注释：暂停与注销的分界线是数据）。于是现状是一个两难：

- 想省内存 → 只能 `Deprovision` → **用户的记忆没了**；
- 想保住记忆 → 只能常驻 → 内存按**注册租户数**走，而不是按**活跃租户数**走。

`Disabled` 不是这个缺口的答案：它保留入口（因此 12 个 fiber 一个不少），只是让它们不实例化、跑不起来。它是**运维语义**（"临时停一下"），不是**容量语义**（"没人用就别占着"）。

## 决定

引入租户的第三态「冷」，并明确它与既有两个状态的分界。**是否采纳，取决于一个可测的比值，见第 6 条。**

1. **冷态的定义**：租户的入口子树**被移除**，但 `Spec`、`CreatedAt`、额度账户、指标计数器，以及**记忆存储里的数据全部保留**。冷租户的下一次请求按需重建入口子树（revive），之后行为与从不曾被回收的租户完全一致。

   三态对照——分界线是"入口在不在"与"数据在不在"：

   | 状态 | 入口子树 | 可寻址 | 记忆 | 恢复方式 |
   | --- | --- | --- | --- | --- |
   | 热（今天唯一的状态） | 在 | 是 | 在 | — |
   | **冷（本条新增）** | **不在** | 否，首个请求触发重建 | **在** | 自动，数据面首请求 |
   | 暂停（`Disabled`，已有） | 在，不实例化 | 是 | 在 | 运维显式恢复 |
   | 注销（`Deprovision`，已有） | 不在 | 否 | **被清除** | 重新开通，从头开始 |

2. **空闲判据必须同时满足三条**，缺一条都不许回收：

   - 该租户此刻**没有在途 run** —— 取 `admit` 的按租户在途读数，不新造计数器；
   - 该租户在窗口内**没有活跃会话**；
   - `now - lastActivity > EvictAfter`。

   `lastActivity` 由数据面读路径打点（单次原子写），不打在控制面：控制面只知道"装配过"，不知道"有人在用"。

3. **revive 必须单飞**。同一租户被并发首请求唤醒时只能装配一次，否则 N 个并发请求会各自装配、互相撞上 `ErrDuplicateTenant`，把一个"冷启动"变成一串 5xx。这是本条最容易被漏掉的一处：判据里没有它，测试里也不会自然地覆盖到。

4. **回收与唤醒都不是破坏性操作，因此允许"误回收"**。janitor 判定与请求到达之间存在竞态窗口，窗口内被回收的租户只会付出一次重装配的代价，不会产生错误的结果。这个性质必须写进文档，否则下一个人会把"刚回收就来请求"当成缺陷去修，而正确做法是让它**可观测**（第 5 条的指标）而不是消灭它。

5. **首次落地默认关闭**（`EvictAfter = 0` 表示不回收，与今天行为逐字一致），由装配方显式打开。理由：打开它会同时改变内存曲线与首请求长尾，而这两条都要在真实流量下取数；把默认值翻过来应当是**下一次**改动，带数据。这也是本条唯一"可逆"的那一步——保留它，就保留了"改错了能退回去"。

6. **采纳判据（决定要不要做的那把尺）**：

   回收省下的是 `(注册租户数 − 活跃租户数) × 30 377 B`。因此：

   > **注册/活跃比 < 2 时不要做。** 2000 租户/片的容量公式本来就够，此时引入 janitor、revive、单飞与一条新的首请求长尾，换不到任何东西。

   这条判据要写在实现之前，因为"回收"一旦被实现，就有动力被默认打开。

7. **janitor 的归属按分片，不按平台**。cordis 的入口操作必须在分片的 `App` 调度 goroutine 内执行，因此回收只能是"分片自己的事"。一个进程级 goroutine 逐个片去调，会让最慢的一片拖住其余所有片；一片一个 goroutine 则各自独立（空闲时只是一次定时唤醒）。它与开通/注销共用同一条批量纪律：**一个 `DoSync` 批次处理一批租户，`Wait` 每批最多一次**（[ADR-0007](0007-fix-on-first.md) 第 1 条）。

8. **冷租户不 `metrics.Forget`**。指标基数因此等于**注册租户数**而非常驻数——这是本决定明确接受的代价（第「后果」节列了它的后果与缓解），因为回收计数器的代价是"每个被回收的租户都在监控图上断一条线"，那会让排查比省内存更重要。

## 后果

**更容易：**

- 内存从"注册租户数"改由"活跃租户数"决定。10 万注册 / 5 千活跃的场景下，常驻从约 3.0 GB 降到约 150 MB（按 30 377 B/租户）。
- 分片数的意义变了：它从"决定能注册多少租户"变成"决定能同时活跃多少租户"。这两个数通常差一到两个数量级，也就是说容量规划第一次有了弹性。

**更困难：**

- **多了一条首请求长尾。** 冷租户的首个请求要付一次装配成本（实测开通 17.6–27.8 µs/租户 + 一次 `Wait`），而 `Wait` 的那一轮会扫过该片全部 fiber。冷启动的 p99 与热路径的 p99 不是同一个分布，监控必须分开看；把它们画在一条线上会让每次长尾都被读成"平台变慢了"。
- **janitor 与开通/注销共享 `App` 的调度通道。** 它占用的是同一个单 goroutine 调度器，因此批量纪律从"建议"变成"必须"——一个每租户一次的回收会把它变成一个新的 O(N) 热点，且只在规模上暴露。
- **多了一个竞态窗口需要被解释。** "刚回收就来请求"会让某个请求比平时慢一个装配周期。它不难处理，但它需要一个不把它当 bug 的读者——而默认的反应是把它当 bug。
- **冷租户的指标基数不变**（第 8 条）。这意味着"监控先挂"的那条风险没有被这条决定消除：`metrics.Registry` 的 label 基数仍随注册租户数增长。省下的是 fiber 内存，不是指标内存。要连指标一起省，得先接受"回收即断线"，那是另一条决定。
- **`lastActivity` 是数据面写、控制面读的一处共享状态。** 它必须是无锁的（请求路径上不能加锁），因此它天然只是"近似最近活跃时间"。这对第 4 条是可接受的；但若有人把它当成精确审计依据（"这个租户最后活跃于……"），它会给出一个偏早的值。

## 落实位置

本决定尚未实施。计划中的符号与它们的职责——**写符号名，不写行号**：

| 位置 | 计划体现 |
| --- | --- |
| `tenant.Manager.Evict(ids)` | 摘入口子树但**不清记忆、不 `Forget`**；与 `Deprovision` 的分界必须写在函数注释里，否则两者会被合并回去 |
| `tenant.Manager.revive`（内部，经既有 `Ensure` 暴露） | 按保留的 `Spec` 重建子树；被唤醒的租户对调用方与"一直在热态"的租户不可区分 |
| `tenant.Manager` 的单飞表 | 每租户一次装配，键的生命周期与冷态集合一致，且必须有对应的清理（否则它自己成为一条无界增长路径） |
| `tenant.Manager` 的冷态集合 | 保留 `Spec` / `CreatedAt`；它是 `List()` 的输入之一——`List()` 不能因为回收而"少了一个租户"，那会让隔离自检与指标静默漏掉它 |
| `tenant.Tenant.lastActivity` | 数据面读路径上的单原子写 |
| `shard.Shard.SweepIdle(now)` | 片内回收入口；一个 `DoSync` 批次，`Wait` 每批一次 |
| `shard.Config.EvictAfter` | `0` = 关闭（首次落地的默认值） |
| `shard.Shard` 的 janitor goroutine | 生命周期与 `Shard` 对齐（`New` 起、`Close` 停），`Close` 必须等它退出 |
| `insula.Config.EvictAfter` | 透传到各片；只在 `shard` 层解释一次 |
| `metrics` 的 `insula_tenant_evictions_total` / `insula_tenant_revives_total` | 成对计数："回收了但醒不过来"必须能被看见（只有 evictions 时它看起来是纯净的收益） |
| `caps` 的 `Ready` | 冷租户的 `Missing` 必须在 revive 之前**不被**当成"能力损坏"——那是两种不同的不 Ready |

守住本决定的断言（实施时**必须补**，写成清单而不是"记得测"）：

| 计划中的测试 | 断言什么 |
| --- | --- |
| `tenant.TestEvictKeepsMemoryAndFiberDoesNot` | 回收后：入口子树 fiber 数归零、记忆仍在、额度账户仍在、指标仍在 |
| `tenant.TestReviveIsIndistinguishableFromNeverEvicted` | 唤醒后的租户与从未被回收的租户在能力快照与一次 run 的结果上不可区分 |
| `tenant.TestConcurrentReviveProvisionsOnce` | N 个并发首请求只装配一次（第 3 条）；变异验证：去掉单飞必须变红 |
| `tenant.TestEvictRefusesWithInflightRunOrLiveSession` | 在途 run / 活跃会话存在时拒绝回收（第 2 条的两个否定分支都要各有一条） |
| `tenant.TestEvictedTenantStillAppearsInList` | 冷租户不因回收而"消失"，自检与指标不漏掉它 |
| `shard.TestSweepIdleUsesOneWaitPerBatch` | 回收走批量纪律（[ADR-0007](0007-fix-on-first.md) 第 1 条），不是每租户一次 `Wait` |
| `shard.TestJanitorStopsWithShard` | `Close` 后 goroutine 退出（`-race` 下不能有泄漏的写） |
| `tenant.BenchmarkEvictAndRevive` | 回收/唤醒的每租户成本与 fiber 净减少，进 `BENCHMARK.md` 的门禁表 |
